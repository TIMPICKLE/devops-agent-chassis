# 模型接入边界与服务器实测排错

本文针对仓库的直接 API 参考适配器。底盘核心不预设某个模型的推理能力、速度或网关行为；接入前需核对实际协议与业务验收。

## 当前支持什么

| 项目 | 实际能力与限制 |
|---|---|
| OpenAI 兼容入口 | Chat Completions 原生 function calling，单调用或显式开启的独立批次；不是 Responses API |
| Anthropic 兼容入口 | 原生 tool use，单调用或显式开启的独立批次 |
| 响应传输 | 当前两种参考路径均按非流式完整 JSON 解析；没有 SSE 增量解析器或 `stream` CLI 开关 |
| 不安全批次 | 执行前整批拒绝，不丢弃剩余调用、不自动串行，见[并行说明](PARALLEL_TOOLS.md) |
| HTTP 错误 | 提取有限安全诊断，保留请求预算与未知用量状态；不自动改参数或重试，见[HTTP 诊断](HTTP_DIAGNOSTICS.md) |

若网关只支持 SSE，当前参考适配器不兼容，这是尚未实现的接入能力。仅将 `stream` 改为 `True` 不能完成支持：还需要重组工具 ID、名称与 JSON 参数片段，识别完整结束与中断，保留用量，并确保完整响应预检通过前不执行工具。

排查网关限制时，应先区分**请求体大小、响应体大小、响应等待时间与流式支持**。启用响应流式并不会移除请求里的任务、知识和工具 schema；不能据此保证绕过请求体大小限制。复现需要网关配置或经脱敏的失败状态及相关计数，不能仅凭一次超时确定原因。

源码：[OpenAI 请求与响应](../adapters/openai_runtime.py)、[共享传输与用量记录](../adapters/runtime.py)。

## 如何判断超时

`Model transport failed or timed out` 是网络/传输失败的汇总信息，单靠这句话不能判断是否发生模型推理过久、代理断连或其他网络问题。应保留每次失败的运行证据，按调用序号核对耗时、结果、可用用量及服务端日志。

| 设置或记录 | 含义 | 调整依据 |
|---|---|---|
| `--timeout` | 传给网络传输的超时参数，不是整项任务的硬性总时限 | 单次调用耗时和网关超时设置；多次调用累计耗时可超过该值 |
| `--max-tokens` | 发给服务端的输出预算；具体模型如何计入推理 token 由协议实现决定 | 输出截断证据及服务端模型说明；增大它不能保证消除超时 |
| `--max-calls` | 模型请求次数预算，失败请求也占次数 | 任务所需的读取、提交与修正轮次 |
| `input_tokens` / `output_tokens` | 服务端返回的用量；无可信数据时为 null | 未记录推理 token 明细时，不能反推出超时是由推理 token 耗尽导致的 |

需要输出完整源码时，先测量输入与预期输出规模，并由业务方决定是否提供有客观验收的局部修改工具。不能通过截断候选源码来冒充完成，也不能仅凭模型名称断言它是否使用推理。

## 装配与验收的归属

仓库已经有 [assemble_employee.py](../tools/assemble_employee.py)：受支持需求缺少必填材料时返回 `needs_input`，退出码 2，不请求模型。但它是受限员工生成入口，不能强制任意外部编程助手逐字执行八组访谈。装配 Skill 是工作指导，实际安全与正确性仍由配置、工具权限和验收代码落实。

`DoneCriteria` 只读事实与外部状态，**不意味着“只要有 diff 就足以修好问题”**。若业务判据仅检查内容变化，`succeeded` 就只证明满足该判据。编译、声明与引用一致性、扫描问题消失等，应由该业务载荷接入相应检查；底盘不硬编码业务规则。

同样，`max_parallel_tools=4` 只说明允许的并发上限；实际发生并发需看 `execution.batches` 和 `parallel_observed`。装配报告中的权限列表证明已配置的权限边界，实际操作还必须经过权限检查，不能用列表替代运行证据。
