# b. 具体需求

> 版本：2026-09-10。业务数据沿用团队提供材料，不在此次文档更新中重新核验。

## 业务背景

研发团队每天都要处理一批有明确输入、重复出现、可以检查结果的工作。SonarQube 异味需要筛选、分派、修复、建 PR 和通知；Azure DevOps 工作项中的需求需要阅读上下文、拆分步骤、修改代码、验证并回复交付结果。人工反复执行这些流程，消耗了本可用于架构设计、业务判断与复杂问题处理的时间。

团队已经积累两类可展示成果：SonarQube 自动治理覆盖 3 个 BU，历史统计包含 911 条处理记录、637 条成功记录及 3667 分钟扫描器预估修复工时；AzureCodeAgent 已基于底盘装配，并由项目维护者确认实测可用。前者证明需求的真实价值，后者证明底盘已经被实际业务采用。

## 需要解决的核心问题

新建第二、第三个数字员工时，团队仍然要重复处理流程控制、模型接入、知识传递、权限限制、失败记录和交付验收。重复建设让单点 AI 效果难以转化为组织级能力。

同时，数字员工的维护周期长于一次代码生成：工作规范会变化，人工会修改生成的代码，服务可能重启，外部接口可能超时。我们需要把“能执行一次”推进到“能重复执行、能判定结果、能维护升级”。

## 功能需求与当前落点

| 需求 | 应交付什么 | 当前实现与范围 |
|---|---|---|
| 岗位经验结构化 | 任务来源、操作步骤、例外、知识、权限、完成标准 | 访谈式装配 Skill、载荷接口、装配清单；仍需业务方提供接口和标准 |
| 批量装配数字员工 | 复用核心，生成或接入不同业务载荷 | 通过需求访谈生成业务载荷与装配脚本，接入实际服务并验收；AzureCodeAgent 已完成业务装配 |
| 任务有序处理 | 接收快、重复事件去重、状态可查询 | AzureCodeAgent 已有 SQLite 队列、后台调度、同工作项串行和中断处置 |
| 模型与流程分工 | 模型处理任务理解与代码生成，程序控制接入、门禁及交付 | 底盘外层编排与内层推理分离；Azure 使用 Nested + Plan-and-Execute |
| 结果可验收 | 检查代码、步骤与交付回执 | 独立 DoneCriteria；Azure 结合静态检查、可配置项目测试及辅助 LLM Review |
| 知识可维护 | 按执行时机提供规范，版本变更可追踪 | 注入与消费回执；参考员工支持知识内容更新、保留人工修改及重新验收 |
| 失败可处置 | 失败分类、记账、补偿和明确人工接管点 | 底盘失败策略与 Ledger；Azure 对重启中断任务阻塞后续同工作项任务，人工核对后解除 |
| 模型与系统可接入 | 支持既有模型服务、Coding Agent 与 MCP | 底盘适配层支持 OpenAI/Anthropic SSE；Azure 复用业务模型客户端和 Claude Code CLI |
| 运行可复核 | 版本、工具调用、验收结果、失败原因关联 | Observer、EvidenceObserver 和独立核验入口；具体业务遥测完整度由接线决定 |

## 验收要求

1. **业务闭环**：从真实任务输入追踪到候选代码、检查结果及交付回执。接收入队、模型结束、创建 PR、人工合入是不同状态。
2. **复用边界**：新增员工在载荷和装配层实现业务逻辑；记录使用的底盘版本及实际改动。不能仅用一个示例文件的行数代表完整业务接入成本。
3. **交付质量**：项目配置真实测试命令，并保留人工审查。模型的完成声明不单独决定成功；辅助 LLM Review 也不替代编译和业务测试。
4. **失败可解释**：未完成验证不能发布；已产生的评论、分支或 PR 要如实记录，不能用“失败零副作用”掩盖已发生的外部动作。
5. **持续维护**：规范更新后验证新行为，同时回归已有任务；保留团队修改。当前知识更新能力不承诺自动合并任意流程或工具代码变化。
6. **运行可移交**：输出启动方式、配置说明、依赖、版本与故障处理手册。核心包无必需第三方依赖，不代表整套业务应用无需安装 SDK、执行器和编译工具。

## 用户范围与收益

直接用户是 PM、质量负责人、开发者和审查者；平台用户是需要装配新岗位的工程团队。近期优先复制研发域内有清晰验收标准的任务，再按接口和验收成熟度拓展到其他部门。

团队已有材料中的每 10 条异味管理约 65 分钟、开发约 10–300 分钟、自动化后审查约 20 分钟，作为原业务测算假设保留。“节省约 90%”沿用团队原测算口径，不等同于本次代码审阅新测得的结果。后续统一记录实际采纳、审查返工、模型费用和接入维护工时，衡量净收益。
