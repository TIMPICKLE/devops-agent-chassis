# Agent Chassis 工程底盘 · 比赛演示与答辩

> 配套 [16 页 HTML 演示](e-演示文稿.html)。主讲 8 分钟，前两项业务案例用于引入，后半段直接展示底盘交付物、装配过程和实际复用代码。

## 1. 核心定位

**本次交付物是 Agent Chassis 工程底盘：引导式 Skills + 预置工程组件 + 运行契约。**

它为 DevOps 团队提前准备需求访谈、组件选型、编排、接入、知识注入、失败处理与可观测能力，再根据用户的业务需求生成载荷和装配脚本，接入实际服务并验收。

聊天里的“一套 DevOps 预制菜”很适合口头解释：通用工程部分提前做好，新业务按需要选用和组合。正式名称仍然使用“Agent Chassis 工程底盘”。“开箱即用”指这些工程资产可直接复用，业务接口、模型服务、凭据与验收标准仍需配置。

### 三个仓库各自扮演的角色

| 项目 | 比赛中的角色 | 应展示什么 |
|---|---|---|
| devops-agent-chassis | **核心参赛交付物** | Skills、组件源码、契约、示例与验证 |
| AzureCodeAgent_Base_Agent_chassis | 基于底盘装配的实际产品 | 用户需求、运行结果、装配脚本、复用关系 |
| SonarqubeAutoFlow_MAF | 业务成果与工程经验来源 | 跨 BU 治理数据与实际任务交付 |

Sonar 当前使用 MAF；Azure 直接使用底盘。先展示两个应用能够让评委理解用途，随后要回到“用户拿走什么、如何使用这套底盘”。

## 3. 关键话术

### 开场：先说交付了什么

“我们交付的是 Agent Chassis，一套面向 DevOps 的工程底盘。里面有引导式 Skills、预置工程组件和运行契约。用户描述自己的业务需求，装配助手按这些指引生成载荷和流程，再接入工具并验证。先给大家看，用这套底盘做出的 AzureCodeAgent。”

### 案例转到底盘

“做完 Code Agent 和代码治理以后，我们发现，很多 AI 提效项目最终都要重复做 Agent 编排、接口接入、知识注入、失败处理和可观测。我们把这些共同部分提前做好，形成了这套可以复用的工程底盘。接下来直接看仓库里交付了什么。”

### 解释 Skills 的作用

“这套 Skills 会引导用户把任务入口、完成标准、知识、权限和异常处理讲清楚，再根据需求选择组件、生成载荷和装配脚本。我们预先规定必须考虑哪些工程问题，具体工作流仍然按用户的业务来装配。”

### 解释 Harness 的作用

“我们把模型放到需要判断和编码的位置，把工具权限、执行预算、验收与交付规则落实到工程代码里。业务流程可以换，但运行要遵循选定的合同。这样，下一个团队能复用已经实现的工程能力。”

### 结尾：留在交付物上

“今天可以交付并拿走的是 Agent Chassis 工程底盘：源码、Skills、预置组件、装配示例和回归验证。AzureCodeAgent 已经展示了它如何落到真实业务。希望下一位使用者可以直接从这些现成能力开始，搭建自己的 DevOps 数字员工。”

“蒸馏真人员工的工作流、批量装配数字员工”可以作为最后一句延伸，不再占用多页概念或远期路线图。

## 4. 现场应打开的交付物

### A. 装配入口：Skills

[装配 Skill](https://github.com/TIMPICKLE/devops-agent-chassis/blob/main/.claude/skills/assemble-digital-employee/SKILL.md)

只展示访谈流程和组件选型表：任务与判据、编排、推理、知识时机、失败策略、权限、观测及模型/工具接入。强调这些指引最终会生成代码和运行配置，并要求实际运行验证。

需求表达示例：

> 我需要一台处理 Azure DevOps 工作项评论的数字员工。收到提及后读取任务、生成计划、修改代码，通过项目检查后交付 PR。请确认任务入口、验收标准、工具权限、知识规范和失败处理，生成载荷与装配脚本并实际验证。

本句用于说明装配意图。现场如果只展示已有装配结果，就不要把朗读这段需求描述为刚刚完成了一次新生成。

### B. 底盘组件：仓库中现成的工程代码

| 资产 | 位置 | 看什么 |
|---|---|---|
| 核心底盘 | `src/agent_chassis/` | 公共合同与 Chassis 装配入口 |
| 编排组件 | `src/agent_chassis/orchestration/` | 外层流程、内层推理分别选择 |
| 接入组件 | `src/agent_chassis/integration/` | ConnectorManager 与 MCP/REST 接入 |
| 知识组件 | `src/agent_chassis/knowledge/` | 按时机提供规范与失败反馈 |
| 失败与权限 | `failure.py`、`permissions.py`（核心包内） | 记账、补偿钩子、能力边界 |
| 观测与证据 | `observability.py`、`evidence.py`（核心包内） | 通用记录、Observer、证据输出 |
| 模型适配 | `adapters/` | 协议适配、流式和配置检查 |
| 接线与验证 | `payloads/`、`examples/`、`tests/`、`.github/workflows/` | 复用入口、合同示例和工程回归 |

这些是仓库交付资产。核心包没有必需第三方运行依赖，真实 MCP/模型和业务服务仍需要相应安装与配置。不要把仓库内所有参考模块说成已独立封装在核心 wheel 中。

“DevOps 接口管理器”可以口头概括接入层，但展示时要落到 ConnectorManager、MCP/REST 和业务适配代码。企业特定字段、接口和凭据由装配层提供，Azure 项目是现成的接入参考。

### C. 装配产物：Azure 实际使用了什么

打开 [generated/azure_code.py](https://github.com/TIMPICKLE/AzureCodeAgent_Base_Agent_chassis/blob/main/generated/azure_code.py)，沿真实代码展示：

1. `AzureCommentSource` 和 `CodeDoneCriteria` 定义业务任务及验收。
2. `NestedOrchestrator` 和 `PlanExecutePattern` 负责选定的控制结构。
3. `SkillProvider` 和 `RetryFeedback` 将规范与失败原因送到对应时机。
4. `ZeroSideEffectPolicy` 和 `Ledger` 接入记账与已注册的业务收尾。
5. `RecordingObserver` 和 `EvidenceObserver` 记录过程与结果。
6. `BusinessServices` 挂载实际业务服务，最后 `build()` 完成装配。

再打开 [payloads/azure_code.py](https://github.com/TIMPICKLE/AzureCodeAgent_Base_Agent_chassis/blob/main/payloads/azure_code.py)，说明哪些仍是业务专属实现。评委应看到“共享组件在哪里、业务差异在哪里”。

[底盘贡献分析](https://github.com/TIMPICKLE/AzureCodeAgent_Base_Agent_chassis/blob/main/docs/工程底盘对CodeAgent的贡献分析.md)可作辅助。涉及具体行为时，以实际接线和源码为准；不需要通过重复统计行数来证明有复用。

### D. 运行产物：可观测已经实现到哪一层

打开 [observability.py](https://github.com/TIMPICKLE/devops-agent-chassis/blob/main/src/agent_chassis/observability.py)：`TaskRecord`、`TraceRecord`、`ToolCallRecord`、`HealthRecord` 以及 `RecordingObserver`。展示一份已脱敏的实际观察记录，说明业务接入可复用同一数据结构。

底盘当前提供结构化记录与观察者，可写 JSON。Azure 中的 SQLite 是任务队列数据库。数据库后端和运营看板按部署接入，不能把“有可观测结构”说成已自动生成整套生产数据库和看板。

### E. 业务成果与回归证据

Azure 优先使用一条已经完成且可展示的任务：原评论、计划、diff、检查结果、PR 与回帖。PR 尚未合入时说明“已交付待审”。Sonar 统计沿用团队原材料，不在此次演示修改中重新核验。

底盘工程合同可查看 [分层验收与兼容性运行](https://github.com/TIMPICKLE/devops-agent-chassis/actions/runs/34245972616)。它对应所测底盘版本，支持工程回归结论。

如果需要离线补充演示，在底盘仓库运行：

```bash
python examples/04_swap_payload.py

```

这两个示例在此前报告更新时已经执行成功。它们解释载荷替换与权限/失败合同，属于确定性示例，不代表现场调用真实模型或创建真实业务 PR。

## 5. “为什么用你这个，而不是 DSH？”

### 主回答

“DSH 有插件化能力，也可以在它上面建设所需方案。我们交付的是一套已经针对 DevOps 整理好的工程起点：Skills 引导装配，预置组件负责共用能力，运行合同约束权限、验收和失败处理。AzureCodeAgent 展示了这些组件怎样组合成实际产品。对需要尽快搭建类似 DevOps 工作流的团队，可以从这些现成资产开始，再补自己的业务接口和规则。”

DSH 的插件化定位依据其[官方 README](https://github.com/deepseek-ai/deepseek-harness/blob/master/README.md)。这里比较的是交付范围和接入工作，不是宣称 DSH 缺少权限、扩展或工程治理能力。

### 如果继续追问“那写成一个 DSH 插件不就行了？”

“插件可以作为分发或装配入口，这是可考虑的合作方向。我们目前交付的是独立工程底盘和实际业务装配案例，其中的组件、业务合同与验收资产都可以继续复用。是否接入 DSH，应由使用团队的运行环境和维护需求决定。”

当前没有交付 DSH 插件，不把可行方向说成已有兼容性。也没有同条件竞品性能与成本测试，不预设普遍领先。

### 如果问“为什么不直接从零搭？”

“当然可以从零搭。我们提供的是已经实现的共同工程部分，以及从需求到装配和验收的使用路径。Azure 的接线能够说明具体复用了哪些代码。推广时再记录新团队的接入、审查与维护成本，衡量实际收益。”

## 6. 其他常见追问

| 问题 | 回答要点 |
|---|---|
| 你最终交付什么？ | Agent Chassis 工程底盘：完整源码、引导式 Skills、预置组件、运行合同、装配示例与验证。 |
| AzureCodeAgent 是主作品吗？ | 它是基于底盘装配的产品案例，证明交付物能用于真实业务。 |
| 只是一套 Skills 吗？ | Skills 负责引导与生成，实际运行由底盘组件、业务工具及验收器承担。 |
| 是不是又做了一个 LangGraph？ | 我们专注于 DevOps 常见工作流的装配与运行约定，把共用工程组件组织成可复用交付包。价值要落到实际接线与使用成本上。 |
| 为什么说流程受约束？ | 必须明确任务、工具、知识、权限与完成判据；运行遵循所选检查和预算。流程形态本身按业务需要选择。 |
| 可以换场景吗？ | 通过新的 TaskSource、DoneCriteria、领域工具和装配脚本接入；通用装配不绑定某一种语言或固定修复任务。 |
| “预制菜”是否意味着不灵活？ | 预置的是通用组件和工程约定，业务任务、编排形态、推理方式、知识与工具可以选择和替换。 |
| 可观测数据库也自动生成吗？ | 目前交付通用记录结构与观察者；数据库服务和看板需要部署接入。Azure SQLite 当前用于任务队列。 |
| 模型如何证明完成？ | 判据检查步骤验证和交付回执。具体业务还要提供项目测试，辅助模型 Review 不替代客观检查。 |
| 失败后真的什么都不留下吗？ | 运行已注册的收尾和补偿并记账；已发出的评论或远端变更需要如实记录和处置。 |
| 开箱能用到什么程度？ | 能复用装配流程与组件。业务接口、模型、凭据、知识和验收仍要配置，随后实际验证。 |
| 批量生成的方向是什么？ | 将已复用的装配资产进一步标准化，支持更多岗位和团队。当前主交付已经是可用的底盘与实际装配案例。 |
