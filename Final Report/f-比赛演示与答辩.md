# 比赛演示与答辩

> 与 [HTML 演示文稿](e-演示文稿.html)配套。默认准备 8 分钟主讲，另留答辩时间；实际按比赛规则裁剪。

## 1. 让评委带走的判断

“这支团队已经有实际业务成果，也已经把经验提炼为能复用的工程底盘。根据业务需求装配后能够持续接收任务、执行和验收，这是扩大数字员工应用范围的基础。”

主张是：**蒸馏真人员工的工作流，批量装配可验收的数字员工。**

“蒸馏”具体指显式整理任务、操作、规范、权限、验收与例外；当前没有自动学习任意真人岗位的产品。愿景应跟着可展示的产物出现。

## 3. 开场与转场话术

### 开场

“我先展示两位已经在工作的数字员工。第一位在 Azure DevOps 工作项里接收任务，执行代码修改，通过检查后交付 PR。第二位持续处理 SonarQube 代码治理任务，已经覆盖三个 BU。今天参赛的工程底盘，就是我们为了让这些经验能够复用、让更多岗位不必重复建设而做的工作。”

### 业务成果转到底盘

“两个场景的入口和交付要求不同，但它们都需要决定何时调用模型、何时检查结果、失败由谁收尾。我们把这些共同能力沉淀到工程底盘中。现在 AzureCodeAgent 已经直接使用这套底盘，业务代码负责工作项和 PR，底盘负责通用运行契约。”

### 引出工作流蒸馏

“真人员工的经验里，最有价值的不只是操作步骤，还包括他何时查规范、如何判断做完、遇到例外时找谁。我们把这些经验变成任务源、节点、知识、权限和验收器。岗位因此有了可以版本化、复制和维护的工程表达。”

### 收尾

“我们已经有业务实践、面向业务需求的装配流程和实测可用的 Azure 装配案例。下一步希望与另一个团队共同选定一个高频岗位，提供接口与验收标准，记录接入、审查和维护成本。让批量装配的价值通过第二个团队的结果体现出来。”

## 4. 比赛现场的真实证据操作

### A. Azure 业务演示，优先使用已完成任务

比赛前选定一条可公开或获准展示的真实任务，预先打开工作项、PR、对应运行记录。逐一展示：

1. 原评论指令与工作项验收要求。
2. 计划步骤及实际修改的 diff。
3. 检查结果，尤其真实项目测试是否执行。
4. PR 链接和交付回帖。若尚未合入，明确“已交付待审”。
5. 选一个现有队列状态，解释接收、执行、成功的区别。

不要为了演示临时重复提交生产任务。需要现场触发时使用准备好的演示仓库和任务。`COMMENT_DELIVERY_ENABLED=false` 用于只保留本地候选的演练；真实交付按业务环境已有授权执行。

为提高现场稳定性，准备同一任务的脱敏截图或录像。离线流程图仅解释逻辑，不当成真实运行画面。

### B. Sonar 成果展示

打开已有业务看板或授权截图，按“日期、项目、成功与失败、一个 PR 样例”讲述。业务数据沿用团队材料，不在现场重新跑统计。不要把 3667 分钟 effort 说成财务确认的人力节省。

### C. 底盘复用与失败演示，无模型、无外部凭据

在底盘仓库根目录执行：

```bash
python examples/04_swap_payload.py
python examples/05_permissions_and_failure.py
```

这两条命令在本次文档更新时已本地执行，退出码均为 0。它们是**确定性合同演示**，说明换载荷和失败/权限行为；不是现场模型实测，也不是生产回放。第一条示例的“PR 评论”与真实 Azure 应用的“Work Item 评论”要分开讲。

### D. 从业务需求到数字员工的装配过程

打开[装配 Skill](https://github.com/TIMPICKLE/devops-agent-chassis/blob/68264ed39ae984c1fbbc17662892f2d0aeb58ab1/.claude/skills/assemble-digital-employee/SKILL.md)，说明其访谈与生成流程，再结合 Azure 装配产物展示实际接线。

可用于说明装配意图的需求示例：

> 我需要一台处理 Azure DevOps 工作项评论的数字员工。收到提及后读取需求，生成计划，修改代码，通过项目检查后交付 PR。请先确认任务来源、完成标准、工具权限、知识规范和异常处理，再选择编排方式，生成载荷与装配脚本并实际验证。

这是需求表达示例；实际演示使用已完成的 Azure 装配材料，不将现场朗读需求当作已经执行了新一轮生成。

| 用户与装配助手的交互 | 应查看的产物 | Azure 对应入口 |
|---|---|---|
| 明确任务来源与完成标准 | 任务源、完成判据 | `payloads/azure_code.py` |
| 选择流程与推理方式 | 编排与计划执行接线 | `generated/azure_code.py` |
| 约定知识与工具权限 | 知识文件、执行器配置、连接器 | `knowledge/`、`tools/`、`clients/` |
| 接入实际服务并验证 | 检查记录、运行状态、交付回执 | 实际工作项、运行记录与 PR |

需求生成不绑定单一语言或预设修复任务。新业务需要相应接口、工具与验收标准，装配助手按这些条件生成和接线。支持多种流程形态不表示无需验收即可上线。

### E. 岗位知识与持续维护

展示 Azure 的 `knowledge/code-execution.md` 和装配脚本中的知识注入配置：规范在执行前提供，失败原因在重试前反馈。

再说明规则变化后的维护步骤：确认变更涉及知识、工具还是流程，修改对应资产，保留无关业务定制，重新执行相关验收并回归旧任务。若有已完成的业务更新记录，再展示前后差异与验收结果；不要将维护方案说成已在 Azure 完成的行为对照实验。

## 5. 常见追问与回答

| 评委问题 | 建议回答 |
|---|---|
| 你做的是业务应用还是平台？ | 本次核心作品是数字员工工程底盘。Sonar 说明业务价值和经验来源，Azure 展示通用需求装配流程如何落到实际业务项目。 |
| Sonar 也是这个底盘运行的吗？ | 当前公开 Sonar 项目仍使用 MAF。我们从治理实践中提炼通用能力，再用 Azure 装配版证明真实复用。 |
| 与现有 Coding Agent 有何区别？ | Coding Agent 提供执行能力，我们围绕岗位补任务入口、结果判据、失败处置与证据合同，可复用现有执行器。当前未做同条件竞品评测，不宣称普遍更优。 |
| 做成 Claude Code Plugin 是否就够了？ | Plugin 可以承担装配入口和分发。员工运行还需要 Webhook、任务状态、业务接口及独立验收，因此插件与运行底盘可分层合作。 |
| 为什么叫蒸馏？ | 把真人岗位的操作、知识、权限和例外提炼为工程契约。当前由人员提供经验、AI 辅助装配，不训练模型权重，也不自动模仿任意员工。 |
| 批量生成已经做到哪一步？ | 已支持围绕业务需求访谈，生成载荷和装配脚本，选择编排、知识、工具、权限与验收并接入实际服务，AzureCodeAgent 是实测可用的装配案例。统一岗位库、批次管理和组织级治理属于后续产品化。 |
| 需求生成是否受语言或场景限制？ | 底盘的装配接口不绑定单一语言或固定任务，业务范围由任务源、领域工具和完成判据定义。具体参考脚本或测试样例的输入限制不能当作底盘整体的限制。 |
| 200 行就能接入？ | 轻量载荷与接线可以很小，但业务服务、配置和验收仍有工作量。Azure 保留完整业务模块。我们用实际新增岗位的接入人时评价复用价值。 |
| 模型怎么证明真的做完？ | DoneCriteria 不采用模型完成声明，核对步骤验证和交付回执。真实业务还要接完整项目测试；辅助 LLM Review 不替代客观验收。 |
| 失败真的没有副作用？ | 在未交付的受控工作区可执行清理。已经发出的评论、推送或 PR 不会凭策略名自动撤销，需要记录和处置。 |
| 能断点续跑吗？ | Azure 持久保存任务。重启发现运行中任务会标为 interrupted，先人工核对再解锁后续任务，不盲目重复外部写入。任意步骤续跑尚未实现。 |
| 7 种推理模式都用生产数据证明了吗？ | 模式接口已提供，真实路径主要按场景使用 ReAct 或 Plan-and-Execute。全部模式的统一效果比较尚未完成。 |
| 节省 90% 如何得出？ | 沿用团队原业务测算假设。Sonar effort 是另一个指标，Azure 暂未汇总规模收益。后续用实际审查、返工、运行和维护成本计算净收益。 |
| 规范变更会覆盖人工修改吗？ | 当前知识更新工具保留工作副本代码和自定义文件，冲突会阻止应用。任意流程变更的自动合并不在现有范围。 |
| 证据能保证真实性吗？ | 证据把版本、执行与判据关联，便于复核。内容 ID 能检查一致性，不能替代可信采集和签名认证。 |

## 6. 演示操作与备用路径

HTML 无外部依赖，可直接双击打开。底栏支持上一页、下一页、目录、讲稿、全屏及打印。键盘支持方向键、空格、Home/End、N 讲稿、O 目录、F 全屏、Escape 关闭弹层。

讲稿面板出现在当前屏幕，投影时也会显示，正式主讲可关闭。打印模式输出全套幻灯片，可用浏览器“另存为 PDF”。GitHub 文件页只显示源码，需要下载 HTML 后打开。

- 网络不可用：继续播放离线 HTML，使用已准备的业务截图及报告。
- 模型请求慢：切换到已准备的 Azure 任务与装配材料，说明其运行版本与结果。
- 示例失败：展示失败原因和限制，不把失败改写为成功。
- 时间只剩一分钟：跳至 12、14 页，讲可复制岗位包与下一步试点。
