# Agent Chassis 工程底盘 · 比赛演示与答辩

> 2026-09-11 更新，配套 [8 页 HTML 演示](e-演示文稿.html)。围绕五项评审要求讲述，主讲 8 分钟，包含一次贡献分析报告展示。

## 核心定位

Agent Chassis 是面向 DevOps 的数字员工工程底盘。用户描述岗位需求，Skills 引导明确任务、知识、权限和完成标准，组合预置组件，生成员工项目并接入真实服务验收。

工程底盘可以进一步拓展为数字员工工厂：将岗位需求标准化，批量装配员工，分别验收，再统一维护和运营。现有装配能力是基础，批量岗位管理与统一运营是扩展方向。

## 关键讲述

### 两类重复劳动

“研发人员反复处理任务，平台团队反复建设 Agent 的共同工程部分。我们把这些共用能力沉淀到底盘，让业务团队主要提供任务、知识、工具和验收要求。”

### 一棵业务成果树

“工程底盘装配出 DevOps Code Agent 和 SonarQube 异味处理。Code Agent 在工作项里接任务，以 PR 交付结果；SonarQube 代码治理已经覆盖 HSI、Portals 和 DSA。”

此处项目关系按维护者在 2026-09-11 本次需求中的确认更新。现有证据索引中的 MAF 快照描述历史实现；本次没有取得新增迁移版本或重新核验 SonarQube 线上运行。历史统计沿用原日期，不归为本次新测的底盘收益。

### 量化价值

“SonarQube 有 911 条处理记录，其中 637 条成功，成功比例 69.9%。成功记录包含 PR 待审和已合入两种状态。扫描器评估的修复工时是 3667 分钟，实际净节省人时需要进一步采样。Code Agent 的案例报告则体现工程复用：编排接线从约 200 行缩到约 30 行。”

不把 effort 当作实际节省，不把 PR 当作已经合入，不用原测算‘约 90%’替代实测净收益。

### 两种用户体验

“装配者用业务语言描述岗位，助手逐步补齐要求，并产出员工项目。日常用户继续在工作项里发起任务、接收结果，审查者决定是否合入。两种用户都能看到具体产物和明确的下一步。”

HTML 中的指令、回帖与流程都是示意，不冒充线上截图。

### 数字员工工厂

“下一步可以把工程底盘扩展为工厂：岗位包是输入，共用组件承担装配，每位员工分别验收，统一运营负责持续升级。这样可以批量生产服务于不同团队的数字员工。先复制到第二团队，用接入工时、采纳率与运维成本验证收益，再扩大规模。”

## 答辩要点

| 问题 | 回答 |
|---|---|
| 和一个 Prompt 或 Skill 有什么区别？ | Skill 负责装配引导，实际运行依赖底盘组件、业务工具和独立验收机制。 |
| 新岗位需要做什么？ | 提供任务入口、知识规范、工具权限、完成标准和异常规则，复用底盘生成并验证业务项目。 |
| 什么场景优先推广？ | 高频、输入明确、动作可控、结果可验证的 DevOps 任务。候选包括构建失败修复、单测补齐和安全告警处理。 |
| 工厂化已经全部做完了吗？ | 现有基础是底盘、Skills 装配和业务应用；标准岗位包、批量管理与统一运营是扩展方向。 |
| 如何保证结果可信？ | 通过业务检查和外部系统回执判定完成，保留人工 PR 审查。模型自述不单独决定成功。 |
| 失败后能否完全撤销？ | 按业务已注册的补偿动作处理，记录残留动作和异常。不能保证所有外部操作都可撤销。 |
| 如何衡量实际收益？ | 按同类任务记录人工基线、审查、返工、异常和分摊运维人时，再计入模型及基础设施费用。 |
| 为什么选择这个底盘？ | 团队可以直接复用 DevOps 常见工程能力及装配路径。现有通用框架也可实现相似方案，具体取舍应依据接入和维护成本。 |
