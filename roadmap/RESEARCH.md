# Research Basis · 修订版 v2

> 定向复核：2026-09-05。使用官方协议、项目文档和一手工程资料。
> 本文区分“资料已经说明的能力”“对本项目的推论”和“尚未执行的对照实验”。没有穷尽全部产品，也没有产生新的竞品实测分数。

## 1. 本次研究改变了什么

第一版把很多值得关注的方向直接升级为必做工程。本版采用三个筛选问题：

1. 它是否解决当前已复现的问题或首个真实场景的明确需求？
2. 现有执行器、SDK、CI 或组织平台是否已经提供这项能力？
3. 我们能否用可复核的实验，证明新增底盘抽象比简单组合更有价值？

据此，B01–B08 是近期验证主线；持久恢复、OTel、MCP 扩展、A2A 与平台治理进入有条件的 C 系列。任务定义以 [BACKLOG.md](./BACKLOG.md) 为准。

Anthropic 的工程总结建议从简单、可组合的模式开始，再按实际需要增加复杂度；这支持“先验证收益再扩展”，但不证明本项目的具体设计已经优于其他实现。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

## 2. 公平比较：不是“别人只有 Prompt”

### 2.1 已核实的外部能力

| 方案 | 一手资料支持的能力 | 不能据此推断什么 | 对本项目的意义 |
|---|---|---|---|
| Claude Code | 生命周期 Hooks，PreToolUse 可参与工具前控制；另有文件系统/网络沙箱机制。[Hooks](https://code.claude.com/docs/en/hooks)、[Sandboxing](https://code.claude.com/docs/en/sandboxing) | 配置了 Hook 就一定覆盖所有逃逸路径；任意安装环境都已正确启用隔离 | 比较时启用合理原生配置，不把权限或 Hook 当作底盘独占能力 |
| Claude Code + 脚本 + Hooks + CI | 原生 Hook 可接脚本，已有 CI 可运行组织测试；具体组合需在实验中实现 | 该组合一定更便宜，或一定不能复用 | 这是最重要的工程成本基线，允许它具备外部验收与清理 |
| DeepSeek Harness | 官方仓库以 Cordis 插件化为架构基础，并标注 developer preview。[官方仓库](https://github.com/deepseek-ai/deepseek-harness) | 已全面审计其安全、稳定性或全部模型兼容；插件化等于多租户治理 | 不再用“无法扩展”作为差异化；有可比环境时增加实际对照 |
| LangGraph | persistence 区分 checkpointer 与跨 thread store，并支持基于持久状态的恢复等流程。[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) | 状态恢复自动保证外部副作用只发生一次 | 需要持久化时先比较适配成熟实现与自建最小实现的成本 |
| Agent Chassis | 该基线具有任务/判据/载荷、编排与装配扩展点，但有 F01/F02 等限制 | 接口分层已经带来效率或可靠性优势 | 用第二载荷、故障矩阵和接入记录证明收益 |

表中各层存在重叠：执行器也可以有生命周期和策略，底盘也可以选择承载推理。不能通过人为划层证明“没有竞争”。

### 2.2 值得尝试的定位

本项目的差异化假设是：

> 将 DevOps 的任务来源、业务验收、失败处理、上下文装配和运行证据做成可复用契约，降低第二类任务的工程接入与长期维护成本，同时保留更换执行器的空间。

这是待验证的产品假设，不是官方资料替本项目得出的结论。

如果 Claude Code + 脚本 + Hooks + CI 已以更低维护成本覆盖目标任务，应承认结果；可以把底盘收缩为少量可复用的契约/模板，而不是继续增加平台功能。

## 3. B08 的对照实验

### 3.1 方案与控制变量

| 组别 | 方案 | 本阶段要求 |
|---|---|---|
| A | 合理配置的同一 Coding Agent / 执行器 | 必做基础基线 |
| B | 同一执行器 + 脚本 + Hooks + CI | 必做组合基线；允许外部验证与清理 |
| D | Agent Chassis + 同一执行器 | 待评估方案 |
| C | DeepSeek Harness + 等价业务集成 | 条件性扩展；模型、工具或环境不可比时只比较架构 |

A、B、D 尽量固定模型版本、任务信息、基线代码、允许动作、验证器、调用预算、超时和重试上限。不要限制对照方案使用其正常能力，也不要允许底盘获得额外任务答案。

模型、工具或后端无法固定时，逐项披露差异；不能将效果差异全部归因于底盘。若 A 本身无法提供同等级自动门禁，应注明由谁实施验证和控制，并计入对应的人力/配置成本。

建议分别做两类实验：

- **任务执行实验：** 相同案例上比较产物质量、错误放行、成本与人工复核。
- **复用实验：** 在两个实质不同的载荷上记录首次接入和第二次接入的工时、专属代码、共享代码及必要内核修改。

小团队无法完全消除学习效应。至少记录执行顺序，给各方案相当的熟悉时间；可能时交错方案顺序并让不同人员复核。不能拿自己已熟悉的底盘与临时学习的对照工具直接做强因果结论。

### 3.2 数据集与统计口径

先用开发案例调试，再冻结独立测试集、评分器与权限策略。禁止看过失败结果后反复改规则，却仍把同一集合称为未见测试集。

建议起点是每方案 20 个不同案例、每例重复 3 次；A/B/D 共 180 次运行，另加开发、故障和攻击测试，是否执行取决于预算。这是试点规模建议，不是已完成结果或行业标准。

- 在开始前定义合格案例和排除原因。超时、无产物、错误拒绝等运行失败保留在结果中，不因影响分数而事后剔除。
- 同一案例的多次运行有相关性；不要把 60 次尝试当作 60 个独立业务场景。
- 同时报不同案例数、重复次数、成功/失败原始计数及每类任务表现。
- 用相同案例做配对分析；需要区间时按案例分组处理，样本不足时明确仅作描述性观察。
- p95 对小样本很不稳定，应同时提供原始耗时或范围。
- 冻结集中的零次错误只表示“本样本未观察到”，不是生产真实风险为零。

参考 ADK 对终态和工具轨迹的区分，但不强制照搬其某一个评分器。[ADK：Why evaluate agents](https://adk.dev/evaluate/)

本项目的建议是：对验收、允许路径和预算使用确定性断言；对存在多种合法做法的工具轨迹检查必要事件、禁止动作和依赖关系，不要求逐步匹配唯一轨迹。不得要求记录或评判模型隐藏思维过程。

### 3.3 防止验收器“自己证明自己正确”

区分两个层次：

- 运行门禁：底盘的 DoneCriteria / 交付前验证器，决定是否允许交付。
- 独立复核：冻结测试、任务隐藏断言和必要的人审，用于判断运行门禁是否错误放行。

后者不能直接复用前者的结果字段充当正确性真值，也不能被候选补丁修改后用于自证。

“模型说完成但门禁拒绝”是一次被拦截的误报；“系统放行但独立复核发现错误”才是错误放行。报告错误放行数及全部尝试数，另给“已放行结果中的错误比例”，避免大量拒绝掩盖产物风险。

安全测试记录实际动作是否发生，不能只检查模型输出里有没有危险词。所有测试使用隔离环境、假凭据和可回收资源，不攻击生产系统。

### 3.4 业务价值核算

DORA 2025 报告将 AI 视作组织现有能力的放大器，而不是自动改善软件交付的保证；这一结论提示我们不能只测代码生成速度。[DORA 2025](https://dora.dev/research/2025/dora-report/)

建议分别报告：

- 人工净节省 = 原流程人工时间 − 新流程操作、复核、返工时间 − 摊销后的接入/维护时间。
- 运行支出 = 所有尝试的模型/执行器费用 + 可归属的基础设施费用。
- 交付质量 = 采纳率、目标问题解决率、新增回归和不当变更。
- 回本条件 = 有效任务量能否覆盖接入与维护投入。

人工时间与金额先分开；需要货币化时显式写明内部工时成本假设。没有正式业务数据时只给可审计的试点结果，不外推全年收益或裁员规模。

## 4. 前瞻方向：证据、适用条件与边界

### 4.1 MCP：先补实际接线，不追求全协议清单

本次参考 MCP 2026-07-28 工具规范。工具定义包含 inputSchema，可声明 outputSchema；客户端验证、工具列表变化和外部注解的信任都需要按规范及所用 SDK 核实。[MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

对本项目的推论：

- B04 先为实际使用的工具补参数/结果验证和本地权限接线。
- C03 先列出“SDK 已提供”“adapter 已暴露”“有测试”“未覆盖”的矩阵，再决定新增代码。
- 远端工具自称只读不能覆盖本地授权判断；有副作用的工具不通过名称猜测自动替换。
- 不把规范中的 MUST、SHOULD 和 OPTIONAL 混成统一硬要求，也不把覆盖某个子集称为全协议认证。

Tasks 是需要显式协商的扩展，可为长时操作提供任务句柄、状态查询和协作式取消；并非每个普通工具调用都必须支持。[MCP Tasks](https://modelcontextprotocol.io/extensions/tasks/overview)

因此，只有目标 Server 确实返回任务或业务需要长时等待才进入 C03；取消请求成功不代表外部动作已经停止。接入 Tasks 也不等于 Chassis 已拥有完整跨进程恢复。

HTTP 授权规范是可选能力，覆盖受保护资源的授权流程；stdio 不使用同一流程。[MCP Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

因此，目标环境需要 OAuth 时，先评估官方 SDK 的支持，凭据留在授权边缘；不能因为目前使用静态 headers 就判整个 Connector 不成立，也不能让配置清单包含 Secret 值。

### 4.2 A2A：有真实委派方再做

A2A 规范描述 Agent 发现、消息/任务/产物及相关交互；本文链接为动态 latest 页面，实施时必须固定具体版本。[A2A Specification](https://a2a-protocol.org/latest/specification/)

C05 的启动条件是明确的对接团队和任务，不是“演示需要多 Agent”。适配应处理身份、任务关联、取消、超时和预算边界；协议连通不证明任务划分有效，也不允许对方继承本地全部权限。

### 4.3 OTel 与上下文：标准映射，而不是日志越多越好

GenAI 语义仓库提供 agent、模型、工具和用量等遥测字段；属性、稳定级别与正文采集要求应以选定版本逐项确认。[OpenTelemetry GenAI 属性](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/registry/attributes/gen-ai.md)

C02 以组织已有接收端和数据政策为条件。先保留本地结构化事件，再做可选 exporter；不要为对齐动态字段重写 Payload。提示词、工具参数、源码和结果正文默认不采集，必要取证应授权并限定保留时间。

近期 B03/B06 先记录上下文来源、版本、注入时机和消费回执；这可以验证接线，不能单凭“按时机注入”断言效果更好或已防住注入攻击。

### 4.4 持久化：恢复状态与重复副作用是不同问题

LangGraph 的 checkpointer/store 分离可作职责参考；本项目若要自建，先说明为什么现成运行时不适合，而不是默认复制完整工作流平台。[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

外部写入存在“远端已成功，本地未收到响应/未记账”的窗口。下游幂等键的语义与保留期、参数绑定和结果查询决定能否安全重试；本地 checkpoint 无法单独消除该窗口。[AWS Builders’ Library：Idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

因此 C01 必须包含故障窗口测试、对账和人工接管。无法确认的写入不得靠增加重试次数解决；补偿失败要保留残留记录，不承诺把不可逆动作变回“从未发生”。

### 4.5 安全与供应链：可信边界比名词重要

OWASP 建议最小权限、外部输入不可信、对高影响动作实施独立控制，并让审批绑定具体动作、参数与有效期。[OWASP AI Agent Security](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html)

据此，本项目需要区分：

| 控制 | 能解决什么 | 单独不能解决什么 |
|---|---|---|
| 统一工具入口 | 可信调用路径上的参数、权限与审计接线 | 任意 Python/Shell 绕开入口 |
| worktree | 分离候选补丁和原工作区 | 隔离宿主文件、网络与凭据 |
| 进程/容器限制 | 在正确配置和受支持环境中限制执行面 | 自动证明不存在逃逸或配置遗漏 |
| 只读证据接口 | 减少执行代码直接修改判据输入 | 证明证据来源真实或存储防篡改 |
| 审批记录 | 明确谁批准了哪个动作 | 批准后参数变化、重放或越权执行 |
| 哈希/版本清单 | 对照内容和版本 | 单独提供可信签名、真实性或审计存储 |

ACS 的官方介绍聚焦运行时 middleware hooks 与可移植策略控制；这可作为 C09 的适配参考，不是当前仓库已通过的合规认证。[OWASP ACS](https://genai.owasp.org/resource/agent-control-standard-acs/)

SLSA provenance 描述构建来源与输入关系。C08 只在发行或组织要求明确时扩展供应链产物；不能用来源证明代替 Agent 行为验证。[SLSA v1.2 Build Provenance](https://slsa.dev/spec/v1.2/build-provenance)

## 5. 从研究到实施的追踪

| 研究结论 | 近期动作 | 后续选项 | 验证证据 |
|---|---|---|---|
| 简单组合也可能满足目标 | B05/B08 先做一条路径和公平基线 | 按测量结果删减抽象 | 同条件结果与维护成本 |
| 行为契约不能只看接口存在 | B01/B02 修复两个已复现缺陷 | 扩展合同测试 | 回归与失败清理记录 |
| 上下文与终态需独立验证 | B03/B06 接收断言、冻结评测 | C02 遥测适配 | 内容版本、使用回执、错误放行统计 |
| 执行控制应分层 | B04 最小权限、独立验证、仅产出 patch | C01/C09 审批和策略接入 | 违规动作实际未执行及覆盖范围 |
| 复用收益需要第二场景 | B07 记录真实接入 | C06 配置版本治理 | 第二载荷工时与必要修改 |
| 协议有可选能力和版本边界 | 不以全协议为比赛门槛 | C03/C05 | 固定版本的所需能力互操作测试 |
| 企业发行有额外治理成本 | B06 先固定运行版本和证据 | C07/C08 | 试点需求、制品/隔离测试 |

## 6. 资料维护与声明规则

本文的一手资料用于支持具体能力和设计原则，不是对商业产品的全量审计，也不替代本项目的测试。

- 固定版本链接：MCP 2026-07-28、SLSA v1.2；采用时仍需核对实际 SDK/构建工具。
- 动态资料：Claude Code、DeepSeek Harness 默认分支、LangGraph、A2A latest、OTel main、OWASP 和 ADK 文档。实施或答辩前重新核对，并记录工具版本或 commit。
- DORA 2025 是该年度研究，不表述为“所有最新研究的统一结论”。
- 每次采纳新标准先记录版本、所需能力子集、SDK 支持和退出/迁移成本。
- 不把公开文档提供某项功能写成“我们已集成”；不把“我们计划集成”写成“项目领先”。
- 无正式评分表、可核验生产统计或同条件实测时，分别标记假设、作者声明和待验证结论。

**前瞻性应体现为可以低成本演进的边界与可验证的路线，而不是同时承诺实现所有新协议。**

## 7. 首批实现采用的接口依据

2026-09-05 实施复核：

- 参考 adapter 使用智谱提供的 Anthropic 兼容入口 `/api/anthropic/v1/messages`，配置仅存模型名、入口与凭据环境变量名。兼容模式并不等于所有原厂参数在每个网关都支持，仍须以本分支 live 结果验证。[智谱兼容接口说明](https://docs.bigmodel.cn/cn/guide/develop/claude/introduction)
- 原生工具调用参数使用 `input_schema`；为匹配当前逐步 ReAct 调用契约，显式设置 `disable_parallel_tool_use`。这不是实现了模型并行调度。[Anthropic 并行工具调用说明](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)
- 工作流沿用官方现行 `checkout@v7`、`setup-python@v7`、`upload-artifact@v7`，普通回归与付费 live 分开；版本号不是供应链审计结论。[Checkout](https://github.com/actions/checkout)、[Setup Python](https://github.com/actions/setup-python)、[Upload Artifact](https://github.com/actions/upload-artifact)

这些资料支持接口选择，不证明本项目已经完成多模型对照或具有成本优势。实际完成状态与限制见 [IMPLEMENTATION.md](./IMPLEMENTATION.md)。
