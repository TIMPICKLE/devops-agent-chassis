# Agent Chassis Roadmap · 修订版 v2

> 更新：2026-09-05；代码审计基线：`bdd2b0a`。
> 已进入 `feat/roadmap-showcase-v1` 分支实施；基线审计仍保留历史语境。逐项完成状态与复现方式见 [IMPLEMENTATION.md](./IMPLEMENTATION.md)，不将首批参考实现等同于全部 Roadmap 完成。

## 先读结论

保留“小底盘 + 业务载荷 + 访谈式装配”的定位。近期不以重造模型框架为目标，而是证明：

> 在明确的运行边界内，团队可以复用任务、验收、失败处理和证据契约，把现有 Coding Agent / LLM 装配成可重复运行的 DevOps 数字员工。

第一版的工程议题大多有价值，但把可选平台建设写成了近期必经之路。本版把顺序改为：

**修复验收与清理契约 → 一个真实场景 → 第二个场景证明复用 → 与现成方案做对照 → 按实际需求扩展。**

## 1. 规划假设与适用范围

尚未取得公司的正式评分表、比赛截止日期、可投入人力、模型预算及生产系统授权。因此：

- 本文按常见的创新性、前瞻性、扩展性、工程可信度与业务价值组织证据，不声称已经满足正式比赛要求。
- 排期是带假设的工作量估计，不是对比赛日期的承诺。
- 默认以代码质量治理为首个候选场景，复用仓库已有经验；最终只选一个有测试、可脱敏、可回放的代表性任务。
- 比赛默认交付本地 patch 和验收报告。真实 PR、通知、生产变更属于额外授权范围，不是演示所必需。
- 已有生产系统的“900+ 次、3 BU、4 语言”等是 README 中的作者声明；本次没有拿到原始统计，不推断其真假，也不把它等同于当前框架的测试结果。
- 正式评分表到位后，先重排优先级，而不是继续往清单上添加功能。

## 2. 项目边界：哪些要做，哪些不必做

### 2.1 底盘的主要职责

| 部分 | 应承担的职责 | 不应混入的职责 |
|---|---|---|
| Chassis Core | 通用任务推进、验收接线、失败语义、观测与扩展契约 | 厂商 SDK、具体技术栈规则、某个公司的工单字段 |
| Payload | TaskSource、DoneCriteria、领域工具及业务规则 | 复制一套相同的失败处理和审计流程 |
| Assembly / Adapter | 选择组件，接 LLM Gateway 或外部 Coding Agent，传递上下文与凭据引用 | 每接一个模型或 MCP Server 就修改底盘内核 |
| 可信执行与交付层 | 进程/网络/凭据限制、独立验证、获授权后的发布 | 由被执行模型修改验收规则或批准自己的越权动作 |

“新增载荷不修改内核”是扩展目标，不意味着内核自身的缺陷不能修复。

### 2.2 两种合法的真实 AI 接入路径

| 路径 | 做法 | 何时选择 |
|---|---|---|
| 借用 Coding Agent | 在被下放的步骤调用现成执行器，由其负责内部模型循环；底盘验证产物 | 已有 Claude Code 等工具，主要任务是代码修改 |
| 直接接模型 API | 在装配层把现有 `decide/planner/solver` 回调接到真实 API，工具调用经受控入口 | 需要精细控制工具选择、模型用量或非编码任务 |

两条路径任选一条先完成参考实现。**不强制先新增核心 ModelProvider，也不把同时接两个 Provider 作为首个场景的前置条件。** 第二种执行器可在互换需求明确后加入。

保留确定性 Demo 和离线测试；它们负责验证框架行为。另设 live 验证证明真实模型/执行器接入，两者不能互相替代。

## 3. 已有资产与最先要补的缺口

值得保留的资产：

- 外层编排与内层推理分离，便于按任务选择控制结构。
- 任务源、完成判据与领域工具有明确载荷边界。
- 确定性 Connector 调用不必经过 LLM。
- 知识按执行时机路由，具备减少跨技术栈耦合的潜力。
- 已有重试、连接器 Trace、MCP 真实传输测试和 LLM 装配工作流。

这些是设计资产，不自动等于领先竞品的证据。

基线审计最高优先级的两项问题（本实现分支已补修复及回归）：

1. **验收接线遗漏。** 只通过 `with_payload(source, criteria)` 配置验收器，而编排器未另传 criteria 时，任务可能直接成功，验收器一次也不执行。
2. **判据失败未清理。** 编排器返回 FAILED 时，Chassis 只记账；注册的 cleanup 没有执行。

它们影响底盘最核心的承诺，已先于扩展实现处理。历史复现见 [CURRENT_STATE.md](./CURRENT_STATE.md)；当前行为以 [合同回归测试](../tests/test_roadmap_contracts.py) 为准。

同时需区分：

- 注入被记录，不代表文本已经送达执行器。
- 读取 `facts`，不代表内容一定可信；事实还需要受信采集来源。
- “有 diff”只证明文件改变，不证明问题修好。
- 外部最终状态验收与交付前质量门禁是两个职责，不能简单把同一个判据搬到交付前。

## 4. 要验证的差异化，而不是预先宣布的优势

| 差异化假设 | 验证方法 | 什么结果会推翻它 |
|---|---|---|
| 载荷契约减少第二个员工的接入成本 | 相同团队接入第二类任务，记录工时、胶水代码与内核改动 | 与脚本方案相当或更贵 |
| 统一验收/失败语义提高跨场景一致性 | 用同一故障矩阵测试两个载荷 | 仍需每个载荷各自补不同兜底逻辑 |
| 时机化知识注入减少无关上下文 | 固定模型/预算，对比全量注入、按时机注入与无注入 | 质量没有改善，或 token 节省被额外调用抵消 |
| 复用现成执行器降低模型绑定 | 替换执行器适配层，保持任务、验证器和产物契约 | 替换迫使修改大量核心或业务判据 |
| 统一运行证据降低复核成本 | 让评审者盲评不同方案的失败报告，计时并统计正确归因 | 证据包更复杂且不帮助定位 |

Claude Code 已有工具前 Hook 和沙箱；DeepSeek Harness 已将插件化作为核心架构。不能用“别人只有 Prompt、我们有权限/插件”作为比较前提。[Claude Code Hooks](https://code.claude.com/docs/en/hooks) · [Claude Code Sandbox](https://code.claude.com/docs/en/sandboxing) · [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)

本项目候选定位是“可复用 DevOps 任务控制与验收层”，不是声称替代上述产品。比较方案和限制见 [RESEARCH.md](./RESEARCH.md)。

## 5. 比赛路线：四个证据里程碑

阶段用 M0–M3；任务优先级另用 P0/P1，避免第一版把阶段号与优先级混为一谈。

| 里程碑 | 近期范围 | 对应任务 | 退出证据 |
|---|---|---|---|
| M0 契约可信 | 修验收接线、判据失败清理；纠正文档能力声明 | B01、B02 | 两个复现变成回归测试，并覆盖不重试、单次记账 |
| M1 真实执行 | 接通上下文；选择一种 AI 接入路径；限定作用域，只产出 patch | B03、B04、B05 | 一个真实任务在受控环境中完成，并由独立检查验收 |
| M2 质量可量化 | 固定案例、失败/攻击测试、运行证据和用量统计 | B06；设计从 M0 开始 | 冻结测试集上的重复结果、失败分类及风险记录 |
| M3 复用有收益 | 装配第二个场景；对比执行器/脚本方案，Harness 按可比性选做 | B07、B08 | 真实接入成本、效果与限制；不预设底盘一定获胜 |

### M0：修复承诺，不扩大架构

验收器必须有单一、明确的权威来源；重复配置冲突要在装配期拒绝，不能静默选择。判据失败必须执行约定的清理，但不因此重新执行整条业务链。

补偿失败要单独报告，不覆盖原始失败；清理只作用于本任务拥有的资源，不能清除使用者原有改动。

### M1：一个真实员工，端到端走通

建议场景：可复现的代码质量问题或构建失败，真实执行器读取代码、修改允许的文件，输出 patch。

最小步骤：

1. 固定任务输入、基线 commit、允许路径及验收规则。
2. 为执行器提供最小上下文；验证 Skill 文本确实送达，而不只出现 Trace。
3. 在经过验证的进程/容器限制下执行；worktree 仅负责工作区分离。
4. 在不受候选补丁控制的验证环境中运行原有测试、针对问题的断言及路径检查。
5. 输出结果与证据；失败清理。不给模型 push/merge 凭据。

如果最终任务确实需要创建 PR，应拆成“交付前质量/授权门禁 → 确定性交付 → 外部状态确认”；不能用事后的 FAILED 掩盖已经发生的发布。

### M2：让别人能复核，不追求漂亮数字

先制作少量开发案例验证链路，再冻结独立测试集；建议起点为 20 个不同案例，每方案重复 3 次，具体数量受预算约束。它只能支持有限结论，不能证明生产风险为零。

| 指标 | 定义 | 如何使用 |
|---|---|---|
| 任务验收率 | 被独立验证器接受的尝试 / 全部合格尝试 | 与同条件基线比较 |
| 错误放行率 | 系统标记成功，但独立检查认定错误的尝试 / 全部尝试 | 冻结安全/回归集出现一例即阻断发布候选 |
| 拦截到的模型误报 | 模型称成功但被正确拒绝的次数 | 是门禁工作量，不与错误放行混淆 |
| 未授权动作实际执行数 | 已越过执行边界的违规动作，而非模型提出次数 | 报告样本数、攻击类别和未覆盖范围 |
| 人工复核/返工时间 | 审核与修补员工产物的实际分钟数 | 防止“自动化”把成本转移给审核者 |
| 采纳率与新增回归 | 被维护者接受的产物比例、独立回归失败数 | 衡量产物业务价值 |
| 接入与维护成本 | 第二载荷工时、共享/专属代码、后续变更工时 | 证明或否定复用收益 |
| 用量与耗时 | 模型/执行器调用、token、估算费用、p50/p95 | 注明价格日期、用量缺失和小样本限制 |

不预设 90% 成功率或 30 分钟装配作为已证实门槛。先测基线、明确业务可接受范围，再冻结发布阈值。样本中的“0 次”只描述观察结果。

### M3：证明复用与增量价值

第二场景应在任务来源或完成判据上实质不同，例如从代码质量修复切换到构建失败定位，不只是改一个名称。

不要求所有扩展都零改动：若第二场景迫使新增通用契约，记录改动原因，说明旧抽象哪里不够；不能为保持“零核心改动”把底盘逻辑复制到载荷。

运行证据先使用现有 RecordingObserver 加简短版本清单；暂不要求平台 UI、完整 DSL 或注册中心。

## 6. 前瞻路线：有触发条件才建设

| 后续方向 | 启动条件 | 最小实现 | 当前不承诺 |
|---|---|---|---|
| 可迁移的员工运行契约 | 两个以上消费者需要重用装配配置 | 版本化配置/证据 Schema、兼容性测试 | 配置能自动表达任意工作流 |
| 可审计的上下文装配 | 多技术栈规范冲突、上下文成本可测 | 来源/版本/作用域、优先级、注入回执 | 仅靠延迟注入即可防 Prompt Injection |
| 跨执行器一致性测试 | 组织实际需要换模型/执行器 | 同一任务/产物/门禁合同测试 | 不同模型效果完全相同 |
| 持久任务与审批 | 任务需跨进程等待或恢复 | SQLite 步骤记录、过期、认领、对账 | 任意外部写入 exactly-once |
| 标准可观测 | 企业已有 OTel 接收与数据政策 | 可选 exporter、脱敏、低基数字段 | 必须记录所有 Prompt 或隐藏思维过程 |
| MCP 扩展 | 目标 Server 确实使用 Tasks/Auth/resources 等 | 先核对 SDK，再实现所需适配与测试 | 实现所有可选能力才算支持 MCP |
| A2A 互操作 | 存在明确的跨团队 Agent 委派方 | Agent Card/Task 边缘映射 | 协议接通自动带来多 Agent 效果 |
| 多租户与策略中心 | 多团队试点证明需要集中治理 | 逐步外置存储、身份、配额 | 比赛前建完整企业平台 |

MCP 工具 Schema、A2A、GenAI 遥测等提供演进方向；采用标准要记录版本与能力子集，标准本身不构成项目创新证据。[MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) · [A2A Specification](https://a2a-protocol.org/latest/specification/)

## 7. 安全与恢复声明的边界

- **API 门禁不是操作系统隔离。** 可信插件可走统一入口；任意 Python 代码仍可直接访问文件或网络。不可信代码应在独立受限进程运行。
- **worktree 不是沙箱。** 它不隔离网络、宿主凭据或系统调用；沙箱配置和逃逸路径需要独立测试。
- **只读 EvidenceView 不是事实真实性证明。** 验证器、测试基线和证据存储必须独立于执行器；哈希用于一致性校验，不自动提供真实性或防篡改存储。
- **不可逆动作不承诺零副作用。** 补偿可能失败，通知不能“没发送过”；报告实际残留与人工处理需求。
- **结果不明不盲目重试。** 对外部写入超时，先使用下游幂等键或查询对账；无法判断时停在“待人工确认”，不重复执行。

最后一条对应分布式写入的故障窗口：远端已经执行、本地还未记账。仅新增 checkpoint 无法消除此窗口。[AWS Builders’ Library：Safe retries](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

## 8. 工期与范围控制

[BACKLOG.md](./BACKLOG.md) 的 B01–B08 初估共 **18–32 人日**，单人全职加约 25% 缓冲为 **23–40 个工作日**。这是参考实现与有限评测的量级，不含生产授权等待，也不是企业平台交付周期。

先完成 B01/B02 和接入可行性验证，再重估后续任务；模型环境、沙箱平台或真实系统受限时必须调整范围。

- **只剩一周：** 优先验收/清理契约和能力声明；有余量才复用现成执行器做窄场景 smoke。未验证能力不得放进现场“已完成”演示。
- **剩两到四周：** 争取完成受控单场景和有限重复评测，第二场景视实际进度加入；不保证整个计划做完。
- **资源充足：** 做第二场景与公平对照；后续协议/平台能力仍按触发条件进入。

不把团队人数简单除以人日作为交付日期；门禁设计、接入调试和评测分析有顺序依赖。

## 9. 参赛证据与演示

| 常见评审维度（非正式评分表） | 最需要展示的证据 |
|---|---|
| 创新性 | 问题抽象与复用边界，以及对现成组合方案的增量收益 |
| 前瞻性 | 跨执行器合同测试、可审计上下文、标准适配边界和启动条件 |
| 可扩展性 | 第二个载荷的真实接入记录，而不是组件数量 |
| 工程可靠性 | 验收遗漏、判据失败、恶意输入、超时等失败路径的测试结果 |
| 业务价值 | 采纳率、人工复核/返工时间、净收益和生产统计口径 |

建议演示顺序：一分钟说明职责边界；展示一次真实修复；故意制造“模型自称成功但验证失败”；展示清理；切换第二载荷；最后给出对照结果与已知限制。

仅当恢复功能已实现并通过故障测试后才现场演示杀进程恢复。为网络不可用准备注明时间与版本的回放，明确区分回放和实时运行。

## 10. 本版相对第一版的实质修订

1. 不再把核心 ModelProvider 缺失本身判为缺陷；先验证合法接入路径。
2. 将验收遗漏与判据失败未清理列为首要任务。
3. 将外部执行器限制、交付前门禁和最终验收拆开。
4. 加入 Claude Code + Hooks/CI、DeepSeek Harness 等公平基线。
5. 移除“统一入口即可绝对防越权”“checkpoint 即可杜绝重复写入”等过度承诺。
6. 取消无基线的成功率/装配时间承诺；增加人工成本和错误放行指标。
7. 把 18 个平台 Epic 收敛为 8 个近期任务；长期功能改为有条件的选项。
8. 分开已实现、已复现、未验证和规划状态，避免文档修订被理解为代码已修复。

**本版完成的事情是规划修订，不是把计划中的能力实现完毕。**
